The solution

How we close the gap: a reflective evolutionary search.

If the problem is "match Sonnet on ramble→tasks with the small model that ships on-device," the solution is not a single clever prompt — it's a search. We let an LLM propose many small variants of the on-device agent, measure each against Sonnet's gold, keep what wins, and iterate.

This is the family of methods behind GEPA, AlphaEvolve, and FunSearch: LLM-guided reflective evolutionary search.

The approach

A 3-billion-parameter on-device model won't be coaxed into frontier quality by one well-worded instruction. So instead of hand-tuning a prompt, we evolve the agent: an LLM acts as a mutation operator, writing one new variant at a time; an automatic evaluator scores it against the frozen Sonnet gold; the best variants survive and become the parents of the next ones. Crucially the proposals are reflective — the LLM reads the judge's per-case notes on what the last variants got wrong and targets those failures, rather than mutating blindly.

Why this family fits us: it turns "make a small model better" into a measurable, resumable search with a hard ruler, so progress is real (it generalizes to a held-out test set) rather than vibes. It's cheaper and safer to run unattended than full reinforcement learning, yet — per GEPA — reflective evolution can rival RL on exactly this kind of text task.

The search space spans two regimes. Most programs are inference-time — changes to the prompt, the guided output schema, the multi-call topology, or the decoding (the GEPA/AlphaEvolve part, no weight change). Later, a program can be weight-update — a trained LoRA adapter (supervised fine-tuning, preference optimization, rubric-reward RL, or distillation). Same loop; the program just carries a kind.

The vocabulary

One shared language across the code, the logs, and this dashboard (the full landscape and sources live in docs/vocabulary.md):

evolutionary run
one campaign — a single run.sh invocation that keeps producing programs until it hits its target count. Resumable.
program
the unit of progress: one agent variant that was built and evaluated. One row in the run log; labelled progNNN.
sample
one turn of the loop — one call to the mutation operator. A sample may fail to produce a program (a failed sample).
mutation operator
the coder LLM (a headless Claude) that writes the next program.
mutation / crossover
deriving a program from one parent (mutation) or combining two (crossover).
elite
the best-fitness program so far — always kept as a parent (elitism).
inspiration
the second parent fed in: the most recent program, so each new one folds in what the last attempt learned.
program database
the store of evaluated programs and their lineage (our results/ + registry).
evaluator
the scoring stack: a hard verifier (the spec gate) followed by the Sonnet rubric judge.
fitness
the score we maximize, 0–1: 0.5·F1 + 0.25·rubric + 0.25·pairwise (zero-task cases scored binary).
infeasible
a program that fails the verifier (e.g. emits emojis or non-atomic tasks) — its case scores 0.
pivot
a patience-driven restart: after several programs with no new elite, drop the elite and strike out in a fundamentally different direction.
rollout
one generation of the model on one input case.

The loop

The whole mechanism, start to finish:

  1. Pick parents. Each sample, the wrapper computes the elite (highest-fitness program on the dev split) and an inspiration (the most recent program). On the very first sample there are none, so it builds from the stock baseline.
  2. Propose a program. The mutation operator is asked to write exactly one new variant — mutating from the elite and folding in the inspiration — while reflecting on the judge's per-case notes (recorded in program.md) about prior failures. It may edit only the agent code (Sources/SplitAgent), then it builds and runs the evaluator.
  3. Evaluate. For every gold case: the verifier (spec gate — non-empty atomic tasks, no emojis, at most 12) runs first; an infeasible case scores 0. Then the Sonnet rubric judge scores faithfulness, atomicity, actionability, coverage, non-redundancy, and phrasing, plus a head-to-head pairwise verdict vs the gold. These combine into fitness.
  4. Keep or discard. If the new program beats the elite on the dev split it's kept (a new elite). The wrapper records its two parents in the program database and runs the held-out test split — reporting only, never optimized against, so a dev gain has to generalize to count.
  5. Pivot on plateau. After a set number of programs with no new elite (the patience), the run pivots: it drops the elite and continues only from the inspiration, forcing a different approach to escape the local optimum.
  6. Finalize. The program and all its dashboard sidecars (operator, type, cost, duration, pipeline, lineage) are written and committed in one step, so a new row shows up complete.

Two invariants make the numbers trustworthy: the ruler is immutable — the gold, judge, fitness metric, and spec gate can't be edited by the loop, so it can't make the test easier; and gains must generalize from the dev split to the held-out test split.

When a program needs trained weights, it becomes a weight-update program — a LoRA adapter (SFT / preference / rubric-reward RL / distillation), with the same Sonnet rubric serving as the reward signal. Inference-time programs come first; adapter training is the next phase.
