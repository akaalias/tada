The coverage wall

Across 71 experiments — every prompting, retrieval, decoding, pipeline, fine-tuning and preference-learning lever I could find — an on-device 3B model matched a frontier cloud model on four of five quality dimensions, but never on the fifth. This is the record of how far it got, and the controlled test that shows why the last dimension is a wall.

Project overview Live dashboard The verdict

1The question

Move one feature from the cloud onto the device, with no quality loss — if that's even possible.

I'm building a native macOS app with a discovery planner: type a one-line task — "plan a trip to Paris" — and it returns a restated title and exactly seven clarifying questions. Today it runs on Claude Sonnet in the cloud. I wanted it entirely local and native, on Apple's built-in ~3B Foundation Model, with no Anthropic access in the shipping product. The whole project is one question: can a ~20× smaller, on-device model match a frontier cloud model on this one narrow task?

To answer it honestly I built an autoresearch loop: a frozen ruler — 30 held-out tasks, each with a Sonnet gold answer and a Sonnet judge that scores the on-device answer head-to-head — and a mutable agent that every experiment changes. The judge scores each question set 1–5 on five dimensions; quality (0–1) blends the rubric with pairwise win rate. The ruler never changes, so scores are comparable across months of work.

Four findings hold across every row. Atomicity, specificity, naturalness and non-redundancy reached 4–5 — the on-device model phrases questions like a thoughtful human and rarely repeats itself. Coverage — whether the seven questions include the single most decision-critical unknown — sat at 3 in every one of the 71 runs (the only values ever observed, on either gate, were 2 and 3). It did not move for prompting, for retrieval, for elaborate multi-call reasoning, for fine-tuning, for more or reshaped training data, or for preference learning.

The cleanest negative. Preference learning (ORPO) first regressed (0.33) because the pairs contrasted two Sonnet styles, not good-vs-bad judgment — the model learned the wrong correlate. Rebuilding the pairs on-policy (chosen = gold, rejected = the model's own weaker draft for the same task) recovered the loss (0.40, back to the SFT baseline) — confirming the diagnosis exactly — but coverage still did not move off 3. Even a clean, correct preference signal could not teach which unknown matters.

4The confirmation experiment

Hold everything constant. Change only the model. Watch coverage.

If coverage is locked because the harness or the prompt is wrong, then a more capable model would also be stuck at 3. If it's locked because the 3B model isn't capable enough, a stronger model — given the identical prompt, schema, gold, judge, rubric and greedy decoding — should clear it. So I ran two cloud models as the candidate through the exact same harness. The only variable is the model.

Coverage moved the moment the model changed: 3 → 4. It was never the harness — the same rubric that scored the 3B at 3 scores Haiku and Sonnet at 4. Two further details matter:

  • The realistic ceiling is 4, not 5. Even Sonnet — the model that wrote the gold — only scores coverage 4 against it, because "the single most critical unknown" carries genuine variance: two excellent question sets disagree on it. Coverage 5 is not a reliably reachable target.
  • 0.65 is the practical quality ceiling, not 1.0. Sonnet judged against its own gold scores 0.65 (it ties itself 18 times, loses 8). On that scale the on-device 0.44 reaches roughly two-thirds of the frontier's own self-consistency — and matches it on four of five dimensions. The whole gap is one coverage point.

5The verdict

Coverage is a capability ceiling of the 3B base, not a method we failed to find.

Imitation, preference learning, and every inference-time technique in the 2024–2025 literature converge at coverage 3. A more capable model clears it on the identical harness. The remaining gap between the on-device model and the cloud — a single rubric point on a single dimension — is bound to model capacity, and no amount of further training or scaffolding on this base is likely to close it.

What this means for the product. The on-device model is already at near-parity on phrasing, specificity, naturalness and non-redundancy, and reaches ~two-thirds of the frontier's practical quality. The one weakness — occasionally missing the single pivotal unknown — is real but bounded. Three honest paths:

Ship & document

  • Ship the 0.44 adapter; record coverage as a known, bounded limitation.
  • Best fit if local + free + private outweighs one occasionally-missed question.

Redesign around it

  • Turn coverage from a judgment the model must nail into a recall task it can do: surface a few candidate axes (from the corpus of nearest task types) and let the user pick.
  • The only path that actually delivers full coverage to a user, on-device, today.

Wait for a bigger base

  • Re-run this exact harness when Apple ships a larger on-device model; it is now a turnkey regression test.
  • No work until then; outcome outside my control.

My recommendation: redesign the feature around the ceiling — it's the only option that gives the user good coverage on-device now, and it sidesteps a wall that more training won't break.

6Reproducibility

Every experiment is logged with its hypothesis, method, result and a process diagram on the dashboard; the narrative is in the project overview. The frozen ruler (30 gold cases + Sonnet judge), all agent configs, the LoRA training and ORPO scripts, the on-policy draft generator, and the cloud ceiling-confirmation harness are in the repository. The autoresearch loop runs unattended and can request the manual training track when it judges the weights are the answer. The cloud anchors in §4 are reference measurements only and are deliberately kept out of the on-device run log.
